Data Fetching: 서버나 외부 API로 부터 데이터를 가져오는 방법

서버에서 fetch 작업이 이루어지므로 개발자 도구에서 확인 불가
단점: 서버 작업 수행 시간 동안 클라이언트에게 아무것도 전달 하지 않음 ( 서버 처리 시간에 의존적 )
-> loading.tsx를 사용해 로딩 중 표시할 UI 사용

Streaming: HTML을 작은 조각으로 나누어 준비 완료된 조각부터 점진적으로 클라이언트에 전송
-> 각 컴포넌트를 청크로 취급하여 사용

여러 개의 Data Fetching 수행 시 각각의 Time을 더한 만큼 시간이 걸림
-> Promise.all을 사용해 비동기 사용: 두 작업이 비동기적으로 동시에 수행됨
+ Suspense 컴포넌트 사용: 각 fetch 작업을 각 별개 컴포넌트로 분리 후 Suspense로 감싸서 처리 -> 먼저 fetch 되는 데이터가 화면에 먼저 rendering됨

캐싱 <- Next.js는 이게 없으면 속도가 매우 저하됨!
1. Request Memoization
- 동일 엔드포인트로 fetch가 발생할 경우 실제로는 한 번만 발생하고 이를 돌려 씀 (랜더링 종료전까지 유지)
2. Data Cache
- 1과 비슷하나 캐시를 삭제하거나 업데이트 전까지 모든 요청에 대해 지속
- 같은 패치가 수행되면 캐시된 데이터를 씀 (다른 클라이언트도!)
-> Revalidation이 매우매우 중요
- time based: 특정 시간마다 수행
- on dement: 특정 이벤트 발생시 (POST, PUT, DELETE 등)
-> FETCH시 tags 옵션을 설정 -> 이후 revalidateTag(tags)를 사용하여 해당 태그의 캐시를 무효화


3. Full Route Cache
- 3, 4는 둘 다 렌더링 된 결과를 저장하는 캐시
- 서버 단의 캐시
- 모든 서버 컴포넌트가 렌더링된 결과
- 같은 경로로 요청이 들어오면 이를 반환
4. Router Cache
- 하이드레이션이 완료된 컴포넌트들을 저장
- 같은 경로의 요청이 들어오면 이를 반환

- 캐시는 명시적으로 끌 수 있음



Optimization

CWV: Core Web Vital <- Next.js의 최적화 기능 개선 초점, 웹 환경의 품질을 측정하는 지표 (검색 엔진 순위 결정에 반영됨)

LCP: 웹 주요 콘텐츠가 얼마나 빨리 로드되는지
INP: 상호작용에 얼마나 빠르게 응답하는가
CLS: 콘텐츠가 예기치 못한 곳으로 이동하는 경우가 없는지

Image 컴포넌트
- img 태그를 확장한 것, 자동으로 이미지 최적화
-> CLS 최적화 (이미지가 로드되면 다른 요소들이 밀려서 변경됨), 이미지의 크기를 미리 계산해 그 만큼의 공간을 확보하여 레이아웃 영향을 없앤다
- 외부 URL에서 이미지를 불러오려면 config에서 허용설정해야함 + 이미지 크기를 미리 알 수 없어서 width와 height를 필수적으로 지정해줘야 함
-> LCP 최적화 - 이미지 퀄리티를 자동으로 낮춰 로딩 속도 개선, quality로 조절 가능, priority 설정 시 가장 먼저 로드하도록 설정

bare metal
- 운영체제가 하드웨어 위에서 직접 실행
- 매우 높은 성능 필요시 사용
- 메모리, CPU 분할이 어렵고 서버 활용 어려움
 
virtual machine
- VM은 자기만의 OS를 따로 가짐
- 높은 격리 수준
- 자체 OS를 포함하므로 무겁고 부팅 느림
- CPU/MEM 오버헤드

containerized
- 호스트 OS의 커널을 공유하면서 독립된 실행 환경만 격리
- 가볍고 빠름
- DevOps, 마이크로서비스 기본 기술
- VM보다는 격리 수준이 낮고 보안도 조금 약함

컨테이너는 독립된 서버가 아니라 실제로는 리눅스 커널이 가지고 있는 기능을 조합하여 독립된 것처럼 보이게 만든 기술
- chroot: 이 디렉토리를 루트라고 믿어라
- namespace: 세계관을 분리, 각 프로세스에게 분리된 '우주'를 제공
- 네트워크 인터페이스도 독립됨 (가상 NIC, 가상 라우팅 테이블)
- cgroup: 사용량을 제한 ( CPU, 메모리, 네트워크 대역폭 등 )

chroot + namespace + cgroup = 컨테이너 엔진
-> 하나의 작은 가상 서버처럼 보임




[Docker의 개념과 장점]
- 어플리케이션에 필요한 모든 것을 컨테이너라는 독립공간에 격리할 수 있게 해주는 오픈소스
- 라이브러리 , 환경설정 파일 포함, 다른 컨테이너와 완전히 독립 (어떠한 리눅스 시스템에서도 실행 가능)

유연성, 경량성, 교체 가능성, 이식성, 확장성

도커는 클라이언트-서버 모델로 이루어짐
Client(CLI), Docker Host, Registry로 이루어짐

Client: 사용자가 도커와 대화하는 통로
- REST API를 사용해 도커 데몬과 통신

Host: 도커 엔진이 실제로 구동되는 런타임 환경
- 도커 데몬: 실제 작업을 수행하는 뇌, 도커의 서비스 관리
- 이미지: 컨테이너를 실행하기 위한 읽기 전용 템플릿
- 컨테이너: 이미지를 실제 실행한 상태

레지스트리: 도커 허브. 도커 이미지를 저장하는 역할

docker swarm: 오케스트레이션


[도커의 기본 명령어]

- docker build: Dockerfile을 기반으로 도커 이미지를 생성

- docker run: 이미지를 기반으로 새 컨테이너를 만들고 실행하는 명령어
 + 포트 매핑 개념
	-p 8080:80 : 호스트 8080 포트를 컨테이너 포트로 연결 ( localhost:8080으로 연결가능 )
 + 자주 하는 실수: 포트 매핑을 안 해서 접속이 안되는 문제

- docker ps: 현재 실행 중인 컨테이너 목록 출력

- docker rm: 필요 없는 컨테이너 삭제
 + 실행 중인 컨테이너는 삭제 불가( stop 먼저 필요 )

- docker exec: 실행 중인 컨테이너 내부 접속 혹은 특정 명령어 추가 실행시 사용하는 명령어
ex) docker exec -ot my-nginx /bin/bash
실행 중인 my-nginx 컨테이너에 직접 bash 셸 실행

FROM: 우리가 그리고자 하는 이미지에 대한 캔버스를 정의하는 명령어

COPY: 파일이나 디렉토리를 컨테이너 내부로 복사

WORKDIR: 컨테이너 내부에 디렉토리를 만들고 해당 디렉토리로 이동

EXPOSE: 해당 이미지가 실행될 때 컨테이너가 실행 중 사용할 네트워크 포트 (기본값 TCP)
- 실제로 컨테이너의 포트를 노출하지는 않고, 명세로서의 역할만 가짐 (실제로 노출시키는건 docker run의 -P, -p )
 ? -P가 임의 포트에 매칭하면 이건 호스트에서 어떻게 알고 접근?
 ? 같은 Docker 네트워크 컨테이너 끼리는 publish 없어도 상대가 리슨 중인 포트로 통신할 수 있는다는게 무슨 의미고 왜 그런건지


ENTRYPOINT: 무엇을 실행할 지 고정
CMD: 기본 인자 제공
- 실무에서는 잘 안 씀

RUN: sheel 혹은 exec로 명령어를 기술
- 기본적으로 shell로 실행
-JSON array로 파싱, 싸따옴표와 이스케이프 처리 필요

RUN은 이미지 빌드 시에, CMD와 ENTRYPOINT는 컨테이너 실행 시에 사용

## 1. 실시간 강의에서 배운 것

- **RAG**: LLM 재학습 비용이 크기 때문에 프롬프트에 외부 데이터를 넣어 보완하는 방식. Chunk 단위 임베딩, hybrid search(키워드+벡터) → 정제 → re-ranking 흐름으로 구현되며, 지금은 **Agent가 RAG를 tool로 호출하는 구조로 흡수되어 컨텍스트 낭비 없이** 효율적으로 사용됨
- **트랜스포머 구조**: token → Embedding → RoPE+attention → MoE(routing) → LM head 흐름 재정리. **당분간 이 구조를 뒤엎을 새 아키텍처는 없을 것**이라는 관점, QLoRA(가중치 freeze) 개념 학습
- **평가 설계**: 평가 전에 "무엇을(end-to-end vs step별, 결국 둘 다 필요) / 정답이 있는 문제인가 / 어떤 기준으로 채점할까"를 먼저 정해야 함. **"도구와 프롬프트가 가장 중요하고 모델/프레임워크는 바뀌어도 이건 불변"**이라는 핵심 아래, 의도대로 동작시키는 3개 레버(여정 관점의 tool 설계, soft-fail 응답, 시스템 프롬프트)를 배움
- **기술 멘토링(커리어)**: LLM 도입은 보안보다 생산성 이득으로 판단되는 추세, 차별화는 "드러난 기준+숨겨진 기준 역산"으로 의도 파악, 좋은 엔지니어 어필은 기술을 밑바닥까지 파본 경험, AI 시대 평가 기준은 생산성 외에 매출/비용/품질/위험과 **unknown unknowns를 찾는 메타인지 역량**

### 요약
실시간 강의에서는 LLM의 기술적 배경과 역사를 다졌고, 기술 멘토링에서는 지금 시대의 개발자가 갖춰야 할 자세를 배웠다. 특히 **성장형 레드오션**을 찾아야 한다는 새로운 관점과, 취업을 앞둔 **SW 엔지니어로서 나를 어떻게 어필할 것인가**에 대한 인사이트가 특히 유익했다.

## 2. 카테캠 일정 트래커를 만들면서 배운 것
- **BE 우선 설계의 함정**: BE는 어느 정도 익숙해서 구조를 먼저 잡고 수월하게 시작했지만, FE(Phase 5) 작업 단계에서 예상 못한 필수 기능, 권한 문제, 페이지·라우팅 분리 로직 재설계 등 대규모 수정이 발생함. **실제 UX에 더 가까운 FE 계층을 먼저 설계하지 않고 BE부터 작성한 게 원인**이라고 판단 — FE 설계를 먼저 고민하는 것의 중요성을 느낌
- **배포 후에야 드러난 "굳이 쓸 이유"의 부재**: 배포 과정 자체는 매끄러웠지만, 막상 배포하고 나니 "이 웹사이트를 굳이 사용할 메리트가 있을까?"라는 질문이 떠올랐음. 학습용이면서 동시에 실사용성도 노려본 프로젝트였는데, **정작 배포한 나 자신조차 이 질문에 답을 못 했다는 게 가장 큰 문제**로 남음
- **과도한 기능 제한으로 인한 UX 저하**: 일정을 개인정보 문제로 판단해 운영진/개발자만 타 인원을 조회할 수 있게 제한했는데, 그 결과 다른 사람의 진행 상황을 확인할 수 없게 되어 오히려 UX가 나빠짐. **공유 일정 조회는 허용하거나 Agent 기능도 토큰 비용을 감수하고 일반 유저에게 여는 등 더 공격적으로 개방했어야 했다**고 생각함. Agent 기능 자체가 미완성 상태였던 점도 아쉬운 부분

### 요약
시도 자체는 야심 차게 시작했지만, 막상 까보면 알맹이가 부족한 서비스였다. 지금 개선한 뒤 다시 배포한다 해도 **"이미 굳이 쓸 필요 없다는 첫인상이 박혔는데, 다시 연다고 눈길이 갈까?"**라고 자문해보면, 나 스스로도 아니라는 답이 나온다. 일정 관리 웹사이트인 만큼 하루라도 빨리 직접 써보자는 마음으로 급하게 배포한 것이었지만, 그 대가로 첫 배포를 얼마나 신중하게 해야 하는지를 간접적으로 경험할 수 있었다.

## 3. PR 리뷰를 통해 배운 것

Week4 PR 리뷰 과정에서 tool 라우팅(어떤 조회 요청에 어떤 tool을 쓸지) 프롬프트를 고치며 겪은 문제를 원인별로 정리.

- **강조 태그로 우선순위를 해결하려던 문제**: Week1~4가 프롬프트를 계속 누적하는 구조라 같은 주제에 대한 지시가 여러 주차에 겹쳐 있었는데, 이걸 각 주차가 `<반드시>`/`<강제>`로 강도를 올려가며 표현하면 **LLM이 "누가 더 세게 말했나"에 의존하게 돼 오히려 예측 불가능해짐** → 강조 태그를 전부 없애고 override를 조건문/평서문으로만 표현하도록 수정
- **system prompt와 tool docstring은 서로 다른 채널**: 시스템 프롬프트에서 라우팅 조건을 다 반영해도, tool 자체의 docstring이 "나도 이 용도다"라고 선언하고 있으면 **두 채널이 충돌한다**는 걸 발견 — tool docstring까지 시스템 프롬프트와 같은 방향으로 맞춰야 함
- **금지 규칙을 계속 쌓는 방식의 구조적 취약성**: "이럴 땐 쓰지 마라"를 예외 케이스가 나올 때마다 추가하는 whack-a-mole식 대응은 규칙이 늘수록 전체가 더 깨지기 쉬워짐 → 금지 규칙을 쌓는 대신 **각 tool이 실제로 뭘 할 수 있고 뭘 못 하는지 사실 그대로 설명하고, tool 선택 판단은 LLM에게 맡기는 방향**으로 전환

### 요약
표면적으로 드러난 문제는 과도한 분기, 중복된 도구 사용, 프롬프트 구조 자체의 취약성이었지만, 근본 원인은 **각 요소의 역할과 의미를 깊이 고민하지 않고 눈앞의 TODO만 따라 구현**한 데 있었다. docstring 같은 구조적인 부분을 고치는 데 소극적이었던 것도 한몫했다. Agent 시스템을 더 깊이 다뤄볼 수 있었던 주차이기도 했지만, 이번 PR 리뷰를 통해 얻은 가장 큰 교훈은 SW 개발에서 **첫째도 명세, 둘째도 명세**라는 것이다. 구조와 역할을 먼저 깊이 고민하고 명세한 뒤 코드를 작성했다면 애초에 생기지 않았을 문제들이었다. 개발자에게 필요한 것은 단순한 코딩 능력이 아니라 **문제를 인식하고 파악하고 해결하는 능력이며, 이는 AI 시대에도 변하지 않는다**는 걸 다시 느꼈다.

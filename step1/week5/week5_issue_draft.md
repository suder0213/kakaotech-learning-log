## 1. MCP(Model Context Protocol)로 배운 것
- **MCP 개념**: 기존엔 tool을 로컬에 직접 구현해야 했는데, MCP는 이미 구현된 tool을 서버에서 받아와 쓰는 방식. 사실상 tool_call과 동일하지만 구현 위치가 서버로 옮겨간 것뿐이고, **로컬에 직접 구현하면 Claude Code/Codex 등 다른 프로그램에서도 재사용 가능**하다는 게 장점
- **MCP 동작 4단계**: (1) 툴 탐색(Discovery) — 클라이언트가 서버에 연결해 tool 목록·설명·파라미터 스키마를 받아옴 → (2) 툴 선택 및 파라미터 전달(Call) → (3) 서버 측 실행 및 결과 반환(Execution & Return) → (4) 최종 응답 생성(Integration). **결국 MCP 서버의 역할은 "tool을 부르는 것" 하나뿐**이라는 정리
- MCP 서버를 붙이면 tool 이름·설명·사용법이 통째로 컨텍스트에 포함되므로, **필요한 tool만 골라 써야 컨텍스트 낭비를 막을 수 있음**
- Agent가 필요한 이유로 다시 연결: LLM은 태생적으로 비결정적·확률적이라 할루시네이션이 불가피하고, prompt는 결국 "출력을 결정하는 조건"이라는 관점. **few-shot/CoT/tool_call/RAG/skills/md는 전부 "조건(context)을 강화해 원하는 출력을 유도하는 것"이라는 하나의 기술로 수렴**한다는 인사이트
- **Sub Agent**: Main Agent와 독립된 컨텍스트로 작업을 위임해 Main Agent의 컨텍스트를 절약. 반대로 **Multi Agent는 Agent끼리 컨텍스트를 공유하지 않는 문제**가 있고, 그렇다고 모든 tool을 하나의 Agent에 몰아넣으면 tool을 잘못 부를 확률이 올라감
- 그 외: A2A(Agent 간 통신 규약), 모델 단계별 분기(계획은 Sonnet, 구현은 Opus, 검증은 Haiku처럼 용도별로 나눠 쓰기), `/doctor`(스킬 최적화), "Claude 5 이후로는 상위 모델일수록 하네스를 빡빡하게 짜기보단 풀어주는 추세"라는 관점

## 2. 모델 평가에 대해 배운 것
- Agent의 동작은 실제로 평가하기 전까진 그럴듯해 보이는 것(할루시네이션)일 수 있고, **대충 넘어갔다간 배상 책임으로 돌아올 수 있다**는 경각심
- 현재 LLM은 "유창함"은 이미 충족했고, **이제는 "정확함"을 평가할 차례**라는 프레임으로 이번 주 내용을 정리
- 유창함 평가 방법: Human Evaluation(Gold Standard, MOS로 사람 평가를 평균 — 생각보다 훨씬 중요), Perplexity(`P(word|context)` 기반, 주로 base/pre-trained 모델 평가에 사용)
- **정확함까지 평가하려면 BERT Score(임베딩 기반 유사도)처럼 실제 정답 데이터셋이 필요**하고, 결국 "정확함 평가는 데이터 싸움"이라는 결론
- **LLM-as-a-Judge**: 프롬프트로 LLM이 직접 점수를 매기게 하는 방법. 장황함을 무시하고 불필요한 길이를 보상하지 않도록 정제된 프롬프트가 필요하며, **결국 "어떤 질의응답 세트를 만들 것인가"가 평가 설계의 핵심**
- 부가로 양자화(INT4/8/16) 개념도 확인 — 8/16비트는 차이가 크지 않지만, 4비트는 소형 모델(SLM)에서 차이가 커짐

## 내가 이해한 것
- 결국 Week5에서 배운 두 축은 서로 이어져 있다: MCP/Agent 쪽은 "조건(context)을 어떻게 잘 구성해 LLM의 출력을 원하는 방향으로 유도할까"의 문제이고, 평가 쪽은 "그렇게 만든 출력이 실제로 맞는지 어떻게 확인할까"의 문제 — 결국 둘 다 "정답 데이터를 어떻게 잘 만들 것인가"로 수렴함

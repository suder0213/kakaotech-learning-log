-> 근본적으로 다른 동작. 같은 프롬프트라도 파싱이 되고 안 되고가 바뀔 수 있음

LangChain에서는 ToolStrategy 권장
-> 추가기능이 있음(재시도, 파싱 로그 등)
-> 근데 실제로 해보면 파싱 실패가 좀 있음

큰 차이는 없는데, 성능이 안 나온다 싶으면 바꿔가면서 써봐도 좋음

Agent가 JSON 파싱에 실패하는 경우 <- 프롬프트 고치면 보통 수정 됨
-> Agent의 고질적 문제: 어떤 것에서 파싱을 실패했는지 알 수 없음

LLM같은 경우엔 추론을 잘해주는데 SLM같은 경우엔 컨텍스트 유지 능력 등이 많이 떨어져 명시화를 해주는 것이 중요함
-> 컨텐스트를 못 찾는 경우, 하위 프롬프트들에서 반복해서 상기해줘야 하는 경우가 있음

- 어떤 부분을 집중해서 봐야하는지? 해석?
- key - query를 dot product하고 뒤의 단어를 masking 했을 때 어떤 단어가 올 지 예측하는?거?
- 마지막에 softmax해서 0과 1사이로 만들고 다시 value와 곱해서...
-> 중요한 것은 커지고, 중요하지 않은 것은 작아짐 (score이 중요도)
컨텍스트 내에서 위의 것들이 반복되면서 중요하지 않은 것은 빠르게 사라지고, 중요한 것들은 천천히 사라짐 (softamx가 1 이하이기 때문)

Context(Prompt): 모델에 조건으로 입력됨, 이것에 따라서 동작을 함
- 실제 모델의 공개된 Context가 많더라도 70~80% 정도만 인식, Lost in the Middle 현상 발생
- Context를 적정선으로 유지하는게 좋음

하나의 Task가 하나의 Context 안에 끝나도록 해주는게 좋음

모델 선택할 때 공개된 벤치마크를 보고 선정하면 잘 될 가능성 높음

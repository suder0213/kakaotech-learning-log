## Day 1 - 컨테이너와 Docker 기초

### 실행 환경 비교

| 방식 | 특징 | 단점 |
|------|------|------|
| Bare Metal | 최고 성능, OS가 하드웨어 위에 직접 실행 | CPU/메모리 분할 어려움, 서버 활용률 낮음 |
| Virtual Machine | 자체 OS 보유, 높은 격리 수준 | 무겁고 부팅 느림, CPU/메모리 오버헤드 |
| Container | 호스트 OS 커널 공유, 독립 실행 환경만 격리 | VM보다 격리·보안 수준 낮음 |

### 컨테이너의 원리

컨테이너는 독립된 서버가 아니라 리눅스 커널 기능의 조합으로 독립된 것처럼 보이게 만든 기술이다.

- **chroot**: 특정 디렉토리를 루트로 인식하게 만듦
- **namespace**: 프로세스마다 분리된 세계관(네트워크 인터페이스, 라우팅 테이블 포함) 제공
- **cgroup**: CPU, 메모리, 네트워크 대역폭 사용량 제한

```
chroot + namespace + cgroup = 컨테이너 엔진 (하나의 작은 가상 서버처럼 동작)
```

### Docker 구조

Docker는 클라이언트-서버 모델로 구성된다.

- **Client (CLI)**: REST API로 Docker 데몬과 통신
- **Docker Host**: 데몬(작업 수행) + 이미지(읽기 전용 템플릿) + 컨테이너(이미지 실행 상태)
- **Registry (Docker Hub)**: 도커 이미지 저장소

### 주요 Docker 명령어

| 명령어 | 역할 |
|--------|------|
| `docker build` | Dockerfile 기반 이미지 생성 |
| `docker run -p 8080:80` | 이미지로 컨테이너 생성·실행 (호스트:컨테이너 포트 매핑) |
| `docker ps` | 실행 중인 컨테이너 목록 출력 |
| `docker rm` | 컨테이너 삭제 (실행 중이면 stop 먼저 필요) |
| `docker exec -it <name> /bin/bash` | 실행 중인 컨테이너 내부 접속 |

### Dockerfile 명령어

| 명령어 | 역할 | 실행 시점 |
|--------|------|-----------|
| `FROM` | 베이스 이미지 지정 (캔버스 정의) | 빌드 |
| `COPY` | 파일·디렉토리를 컨테이너 내부로 복사 | 빌드 |
| `WORKDIR` | 컨테이너 내부 작업 디렉토리 설정 | 빌드 |
| `RUN` | 쉘 명령어 실행 (레이어 생성, 캐시 활용) | 빌드 |
| `EXPOSE` | 컨테이너가 사용할 포트 명세 (실제 노출은 `-p` 옵션) | 빌드 |
| `ENTRYPOINT` | 실행할 커맨드 고정 | 실행 |
| `CMD` | 기본 인자 제공 | 실행 |
| `USER` | 명령어를 수행할 사용자 지정 | 실행 |

**이미지 레이어**: Dockerfile의 각 명령어 한 줄이 하나의 레이어가 되며, 캐싱에 활용된다.

## Day 2 - 환경변수, 데이터 영속화, 네트워크, Docker Compose

### 환경 변수

```dockerfile
ENV APP_ENV=production
ENV DB_HOST=${APP_ENV}-db   # ${VAR} 형식 참조 권장
```

- 컨테이너 실행 중 참조 가능한 변수
- 접두사를 사용해 충돌 방지

### 데이터 영속화

컨테이너는 삭제되면 데이터도 함께 사라지므로 외부 저장이 필요하다.

| 방식 | 저장 위치 | 관리 주체 | 주요 용도 |
|------|----------|----------|----------|
| Bind Mount | 유저가 지정한 호스트 디렉토리 | 유저 | 소스 코드 공유, 실시간 개발 |
| Volume | Docker가 관리하는 호스트 디렉토리 | Docker | DB 파일, 로그, 설정값 보존 |

- Volume은 호스트 파일시스템에 덜 의존적이어서 대부분의 경우 더 권장된다.
- 이름 미지정 시 해시값으로 생성되어 관리가 어려우므로 반드시 이름을 지정한다.

### Docker 네트워크

컨테이너는 기본적으로 격리되어 있어 다른 컨테이너와 통신하려면 별도 네트워크 설정이 필요하다.

- 기본 드라이버: `bridge` (같은 네트워크 내 컨테이너 간 DNS/IP 통신 가능)
- 컨테이너 이름을 DNS로 사용하려면 사용자 정의 네트워크를 생성하고 컨테이너 생성 시 지정해야 한다.

### Docker Compose

여러 컨테이너를 `docker-compose.yml` 한 파일로 정의하고 한 번에 관리할 수 있는 도구.

```yaml
services:
  backend:
    build: ./backend
    depends_on:
      db:
        condition: service_healthy  # healthcheck와 함께 사용하여 순서 보장
  db:
    image: postgres
    healthcheck:
      test: ["CMD", "pg_isready"]
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

**다중 컨테이너 구조의 장점**
- 변경·배포 독립, 유지보수 용이, 장애 국소화
- 컨테이너별 독립적 스케일링
- 언어·환경 독립 (MSA에 적합)

## Day 3 - 네트워크 기초 & AWS 클라우드

### 네트워크 기본 개념

- **MAC**: 기기에 부여된 고유 번호
- **IP**: 네트워크에 연결된 장치 식별 주소
  - 공인 IP: 전 세계에서 고유
  - 사설 IP: 내부 네트워크 전용, NAT를 통해 외부 통신 가능

### 온프레미스 vs 클라우드

| | 온프레미스 | 클라우드 |
|--|-----------|---------|
| 서버 위치 | 내 컴퓨터/자체 데이터센터 | 외부 데이터센터 |
| 비용 | 초기 비용 높음 | 사용량 기반 지불 |
| 탄력성 | 낮음 | 높음 (스케일 업/다운 용이) |

### AWS 핵심 서비스

| 영역 | 서비스 | 설명 |
|------|--------|------|
| 컴퓨팅 | EC2 | OS·CPU·RAM 등 컴퓨팅 자원 임대 |
| 스토리지 | S3 | 객체 스토리지 |
| 데이터베이스 | RDS | 관리형 관계형 DB |
| 네트워크 | VPC | AWS 내 독립적인 클라우드 네트워크 |
| 보안·인증 | IAM | AWS 리소스 접근 제어 |

**보안 설정**
- **보안 그룹**: 인바운드/아웃바운드 규칙을 인스턴스 수준에서 설정
- **ACL**: 서브넷 수준에서 설정

**IAM 계층**
- Root: 계정 생성 시 이메일로 모든 권한 소유
- User: 실제 작업을 위해 생성하는 개별 계정 (최소 권한 원칙 적용)
